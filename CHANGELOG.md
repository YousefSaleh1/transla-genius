# Changelog

All notable changes to `coding-partners/transla-genius` are documented here.

## [4.0.0] - Unreleased

A breaking architectural release: the translation backend is now swappable behind an interface, translation payloads are typed DTOs instead of raw arrays/strings, and persistence is a separate, narrowly-scoped class instead of being mixed into the queue job. See [UPGRADE.md](UPGRADE.md) for the step-by-step upgrade from 3.x.

### Breaking changes

- **The config file and key are renamed from `translaGenius` to `translagenius`.** The shipped file is now `config/translagenius.php`, and every key is read as `config('translagenius.…')`. There is no fallback to the old name. Rename a published `config/translaGenius.php` to `config/translagenius.php` and update any `config('translaGenius.…')` calls in your code. `php artisan translagenius:check` reports it if the old file is still there. The publish tag (`translagenius-config`) is unchanged.
- **`TranslateFields` is constructed with a single `DTOs\TranslationJobPayload`** instead of positional `($model, $fields)` arguments. If you construct or dispatch it yourself, wrap the arguments: `new TranslateFields(new TranslationJobPayload($model, $fields))`.
- **`TranslatorInterface::translate()` gained two optional arguments**, `?string $field = null, ?string $model = null` (and `DTOs\TranslationRequest` gained matching optional properties). A custom `TranslatorInterface` implementation must add them to its signature. `TranslateFields` passes the attribute name and the model's class basename.
- **`TranslateFields::prepareTranslations()` is replaced by `translateMissingPairs()`**, which saves each translation as it completes instead of returning a map for `handle()` to save. Update any subclass that overrode it.
- **Config shape changed.** The flat `api.*` / `settings.*` keys are gone. Config is now provider-keyed:
  ```php
  // Before (3.x)
  'api' => ['key' => ..., 'url' => ..., 'model' => ...],
  'settings' => ['temperature' => ..., 'max_tokens' => ...],

  // After
  'default' => 'openrouter',
  'providers' => [
      'openrouter' => ['driver' => OpenAiCompatibleProvider::class, 'key' => ..., 'url' => ..., 'model' => ..., 'timeout' => ..., 'temperature' => ..., 'max_tokens' => ...],
  ],
  ```
  Republish the config file (`php artisan vendor:publish --tag=translagenius-config --force`) and migrate any custom values you'd set.
- **`Services\AutoTranslationService` is removed.** If you depended on it directly (type-hinting it, resolving it from the container), depend on `Contracts\TranslatorInterface` instead - `translate($text, $source, $target)` now returns a `DTOs\TranslationResult` (with a `->text` property) instead of a bare string.
- **`TranslateFields::handle()`'s signature changed** from `handle(AutoTranslationService $translationService)` to `handle(TranslatorInterface $translator, TranslationWriter $writer)`. If you extended or directly invoked this job's `handle()` method, update the call site.
- **`Middleware\SetLocale` now requires constructor injection** (`Contracts\LocaleResolverInterface`) - if you were instantiating it directly (`new SetLocale()`) rather than letting Laravel resolve it from the container, that will break. Resolve it via the container (`app(SetLocale::class)`) or Laravel's normal middleware registration instead.
- **`DTOs\TranslationResult` now throws `InvalidArgumentException` if constructed with empty/whitespace-only text.** A custom `TranslationProviderInterface` implementation that previously returned an empty result without throwing `TranslationFailedException` will now fail loudly at construction time instead of silently producing a result nothing downstream expected.
- `Traits\Translatable::scopeFullyTranslated()`'s underlying SQL changed (now driver-agnostic `whereNotNull('field->locale')` instead of MySQL-only raw `JSON_EXTRACT`/`JSON_UNQUOTE`) - behavior is equivalent, but if you depended on the exact generated SQL for any reason, it's different now.
- `Traits\Translatable::hasSourceLocaleChanged()` is removed. The `updated` listener stopped using it when edits started re-translating (it now builds a re-translation plan), so a model calling it from an override must drop the call.

### Added

- `Events\TranslationsPersisted`, fired once per job after its last write, with the record (read again) and the field/locale pairs written. Translations are still written per pair without model events, so observers (Scout, cache busting, audits) are not called once per pair; listen to this event instead, or set `TRANSLATION_FIRE_MODEL_EVENTS=true` to fire the model's `updated` and `saved` events once per job (they don't re-trigger translation).
- An exception hierarchy: every package exception extends `Exceptions\TranslaGeniusException`. Configuration errors (an unknown provider name, a missing key or URL, a missing, short or looping fallback chain, a driver class that doesn't exist or isn't a provider) throw the new `Exceptions\TranslationConfigurationException`, which is never retryable: a translation job fails on its first attempt and fires `TranslationFailed` once. Before, a `TRANSLATION_PROVIDER` typo retried every attempt and fired no event. `AllProvidersFailedException::getFailures()` names each member by its config name, with its class in `class`.
- Models can declare their translatable columns with spatie's `#[Translatable(...)]` attribute (spatie/laravel-translatable 6.14+), on its own or together with the `$translatable` property. The trait no longer overrides spatie's `getTranslatableAttributes()`, and every internal read goes through it, so the package sees the same columns spatie does. Before, an attribute-only model got no translatable columns and `create()` failed with an SQL error.
- Review workflow (`TRANSLATION_REVIEW`, off by default): AI translations of the configured models / fields / locales (`review.models`, `review.fields`, `review.locales` / `TRANSLATION_REVIEW_LOCALES`; everything when none is listed) are stored as pending reviews in a new `translation_reviews` table (publishable migration, `translagenius-migrations` tag) and published only on approval. `TranslaGenius::reviews()` offers `pending()`, `approve()` (optionally with an edit and a reviewer), `reject()`, `retranslate()`, `approveAll()` and `prune()`; approval refuses stale text (`StaleReviewException`, the review is superseded) and won't overwrite a hand edit unless forced (`ReviewConflictException`). `review.while_pending` (`TRANSLATION_REVIEW_WHILE_PENDING`) keeps the stale published text visible (default) or clears it, per model or field; `review.on_reject` (`TRANSLATION_REVIEW_ON_REJECT`) leaves a rejected locale missing (default) or re-requests it. Approved edits update the translation cache (opt-out per approval); rejections evict it. Backfill skips pending pairs and re-requests rejected ones. New `Models\TranslationReview`, `pendingReview()` scope, events `TranslationPendingReview`, `TranslationApproved`, `TranslationRejected`, `TranslationSuperseded`, `TranslationCompleted::$pendingReview`, and commands `translagenius:review:list`, `translagenius:review:approve-all`, `translagenius:review:prune`. With review off nothing changes and the table isn't needed.
- Translation cache (`TRANSLATION_CACHE`, default off; `TRANSLATION_CACHE_STORE`, `TRANSLATION_CACHE_TTL` default 30 days, `0` = forever): identical source text translated with an identical setup is requested once and then served from Laravel's cache, across all records and models. `Providers\CachingProvider` wraps the resolved provider (a fallback chain included) automatically when enabled. Keys (`translagenius:v1:<sha256>`) cover the text, both locales, the provider and its output-affecting settings (model, URL, prompt templates, temperature, `reasoning_effort`, `body`, response format), and field/model context only when a prompt uses `{field}`/`{model}`. Failures, truncated replies and invalid batch values are never cached; in a fallback chain only primary-served results are. Batches send only the cache misses.
- `TranslationResult::$cached` and a `cached` column on `translation_usage_logs`: a cache hit still fires `TranslationStarted`/`TranslationCompleted` and gets a usage row, with no tokens or cost.
- Opt-in batching (`TRANSLATION_BATCH`, default off; per preset `OPENAI_BATCH` etc., or `batch` on an entry): all missing target locales of one field are translated in a single request that returns a JSON object keyed by locale, instead of one request per locale. Replies are validated strictly; missing or invalid locales are requested one at a time, and a reply that isn't JSON, or one cut off at the token limit, sends the whole field one at a time (in a fallback chain, a truncated batch first moves to the next batch-capable member). `openai` batches use a strict `json_schema` response format and `deepseek` uses `json_object`, the two presets whose docs confirm it; the others rely on the prompt. The batch prompt is configurable (`TRANSLATION_BATCH_PROMPT`, `batch_prompt`) with a `{target_locales}` placeholder.
- `Contracts\BatchTranslationProviderInterface` (optional capability, implemented by `OpenAiCompatibleProvider` and `FallbackProvider`) and `Contracts\BatchTranslatorInterface` (implemented by `Services\Translator`). Providers that only implement `TranslationProviderInterface` keep working, one call per locale.
- `TranslationResult::$requestId`, identifying the API request a result came from. The `translation_usage_logs` table ships with a matching nullable, indexed `request_id` column: with batching, one request yields several rows sharing a `request_id`, and the request's tokens and cost are stored on exactly one of them, so summed usage equals what was billed.
- `TRANSLATION_QUEUE_CONNECTION` / `TRANSLATION_QUEUE` (empty = the app's defaults) and `TRANSLATION_DISPATCH_AFTER_COMMIT` (default `true`), applied wherever a translation job is dispatched: model create/update and `translagenius:backfill`, including a `translationJobClass()` override that uses `Queueable`. `TranslateFields` now uses `Queueable`.
- A configurable system prompt for OpenAI-compatible providers: `prompt` in the config (or `TRANSLATION_SYSTEM_PROMPT`), overridable per provider entry, with `{source_locale}`, `{target_locale}`, `{field}` and `{model}` placeholders. Unknown placeholders are left as written, an empty value falls back to the built-in prompt (unchanged), and field content is only ever sent as the `user` message.
- `reasoning_effort` per provider entry, sent only when set, with a variable per preset (`OPENAI_REASONING_EFFORT`, ...). `openai` and `deepseek` default to `none`; the others send nothing unless configured.
- A config-only `body` array per provider entry for extra request fields. It can't set `model`, `messages` or `stream`.
- `Contracts\TranslationProviderInterface` - the extension point for swapping translation backends. Implement it and register it under `translagenius.providers` to use DeepL, Google Translate, another LLM, or an internal service - no changes to the job or trait required. See the README's "Custom Translation Providers" section.
- `Contracts\TranslatorInterface` - the orchestration layer above the provider is now also behind an interface (`Services\Translator` is the default implementation). Rebind it to replace translation-resolution itself (caching, fallback chaining, ...) without touching the job or trait.
- `Contracts\LocaleResolverInterface` - locale resolution (previously two bare global functions with no DI seam) is now a bindable interface (`LocaleResolvers\DefaultLocaleResolver` is the default: `Accept-Language` header + `translagenius.supported_languages`). `get_current_locale()`/`get_supported_languages()` remain as thin backward-compatible wrappers around whatever's bound.
- `Traits\Translatable::translationJobClass()` - override this on your model to dispatch a custom job instead of the default `TranslateFields`, without forking the trait. The class must implement `Contracts\TranslationJob`, a constructor taking one `DTOs\TranslationJobPayload` (the model, fields, source locale captured at dispatch, re-translation plan and options), which every dispatch point builds and passes. `TranslateFields` implements it, so extending it is the easy path. A class that doesn't implement it is rejected at dispatch with `Exceptions\InvalidTranslationJobException`.
- `Contracts\HasTranslatableAttributes` - documents the real precondition `TranslationWriter`/`TranslateFields` depend on (a model with `getTranslation()`/`setTranslation()`, i.e. one using the `Translatable` trait) for static analysis; enforced at runtime by `TranslationWriter` with a clear error message rather than the `BadMethodCallException` you'd otherwise hit.
- `DTOs\TranslationRequest` / `DTOs\TranslationResult` - typed, `readonly` value objects replacing the raw strings/arrays previously threaded through the job.
- `Services\TranslationWriter` - the locked read-check-write step (introduced earlier in this release as part of `TranslateFields`) is now its own small, job-independent class.
- `Facades\TranslaGenius` - convenience facade over `TranslatorInterface` for translating arbitrary text outside the automatic model-save flow.
- `php artisan translagenius:check` - verifies the active database connection's JSON support (MySQL/MariaDB/PostgreSQL/SQL Server unconditionally have it at this package's stated floors; SQLite genuinely doesn't below 3.38.0 without JSON1 compiled in - see the README's "Database Requirements" section).
- `Events\TranslationStarted` / `Events\TranslationCompleted` / `Events\TranslationFailed` - `TranslateFields` now dispatches these at well-defined points in the translation lifecycle, so features like usage tracking or review workflows can be built as plain listeners instead of forking the job. See the README's "Lifecycle Events" section.
- `Providers\FallbackProvider` - a `TranslationProviderInterface` decorator over an ordered chain of other providers, falling through to the next on any failure and returning the first success. Configured as a `driver` like any other provider, with a `chain` key of other provider names resolved through the same config-driven resolution - see the README's "Provider Fallback / Chaining" section. Throws the new `Exceptions\AllProvidersFailedException` (a `TranslationFailedException` subclass) if every provider in the chain fails, carrying each one's individual failure via `getFailures()`.
- `Traits\Translatable::scopeNotFullyTranslated()` - the exact inverse of `scopeFullyTranslated()`, for finding records missing at least one field/locale.
- `php artisan translagenius:backfill {model}` - finds existing records that aren't fully translated and dispatches `TranslateFields` for each, chunked via `chunkById()`. Reports the affected record count and an estimated API-call count before doing anything, and requires `--force` or an interactive confirmation before dispatching (a bare, unconfirmed run dispatches nothing). `--dry-run` reports only. See the README's "Backfilling Existing Records" section.
- `translagenius.usage_tracking` (opt-in, `enabled: false` by default) - when turned on, `Listeners\LogTranslationUsage` writes one `Models\TranslationUsageLog` row per `Events\TranslationCompleted`, with an estimated cost computed from configurable per-provider `cost_per_1k_prompt_tokens`/`cost_per_1k_completion_tokens` rates (`null`, never `0`, when a rate or token count isn't available). Ships the package's first publishable migration (`php artisan vendor:publish --tag=translagenius-migrations`), for the `translation_usage_logs` table this backs. `TranslationUsageLog` is public API surface - query it directly for your own usage/cost reporting. See the README's "Usage & Cost Tracking" section. When disabled (the default), no listener is registered and the migration isn't required.
- Added an opt-in `shouldTranslateField()` hook models can define to filter which field content is sent for translation.
- `Providers\OpenAiCompatibleProvider` accepts an optional `headers` array (merged into every request; null/empty values are dropped) an optional `auth_header` (default `Authorization`, which sends `Bearer <key>`; any other header name sends the raw key), and an optional `token_limit_param` (default `max_tokens`; set `max_completion_tokens` for APIs that deprecate `max_tokens`, such as OpenAI's).
- Ready-made provider presets in the shipped config: `openrouter` (still the default), `openai`, `gemini`, `deepseek`, `mistral`, and `custom` for any other OpenAI-compatible endpoint (Ollama, vLLM, LiteLLM, ...). Each reads its own environment variables, so switching providers is a `.env` change (`TRANSLATION_PROVIDER=gemini` plus `GEMINI_API_KEY=...`). The legacy `TRANSLATION_API_KEY`/`TRANSLATION_API_URL`/`TRANSLATION_MODEL` variables keep working for the `openrouter` default and drive the `custom` entry.
- Failover through `.env` alone: `TRANSLATION_PROVIDER=fallback` with `TRANSLATION_FALLBACK_CHAIN=openai,gemini` (comma-separated, whitespace trimmed, empty items ignored) uses the shipped `fallback` entry. A `chain` may now be an array or a comma-separated string.
- Provider resolution now fails fast with a clear `RuntimeException`, naming the provider key and class, when a `driver` class doesn't exist or doesn't implement `TranslationProviderInterface`.
- `Services\TranslationWriter::apply()` is removed (it was new in 4.0 and unused since the job writes through `fillMissing()` and `applyRetranslation()`). Those two keep its guard against a model without the `Translatable` trait, and are `@internal`.
- The public surface is now marked: classes and methods that are public only for package wiring are `@internal` (the `Support\` namespace, `Console\Concerns\`, `ReviewManager::propose()`, `pairsToSkip()` and `supersedeForSourceChange()`, `CachingProvider`'s key methods, `TranslaGeniusServiceProvider::intSetting()`, and the protected helpers of `TranslateFields`). The README's new "Backward compatibility promise" section says what semver covers.

### Deprecated

- The global `get_current_locale()` and `get_supported_languages()` helpers. They remain, as thin wrappers over `Contracts\LocaleResolverInterface`, for code that calls them. The package itself no longer calls them: they are unprefixed and only defined when missing, so an app that defined its own functions with those names silently changed the package's locale handling.

### Fixed

- With the translation cache on, a cache outage (Redis refusing connections) stopped every translation: the error propagated before any provider call. A cache error is now a miss on read and a skipped write, with one warning per minute per process.
- A fallback chain caught only `TranslationFailedException`, so a custom driver throwing its SDK's own exception skipped the remaining members and fired no failure event. Each member's `Exception` is now a failure of that member, wrapped in a retryable `TranslationFailedException` that names it and keeps the original as `previous`; PHP `Error`s still propagate. A `usage` value that isn't a whole number (`"twelve"`, `3.5`) is now unknown (null) instead of a `TypeError`.
- An accessor on a translatable attribute (a `trim`, a `strip_tags`) made every translation of that field be thrown away: the job planned from stored values but the writer compared accessor-applied ones, so a source of `"Blue shirt\n"` never matched itself and each paid translation was discarded, on every attempt. Every snapshot and comparison (the plan, the writer's checks, the review rules, backfill) now reads stored values through one internal reader.
- One failed pair ended the whole job: a 400 on `ar` meant the other languages were never requested, on that attempt, on a retry, or by backfill, and a truncated `name` meant `description` was never requested. The job now goes on with every other pair, saving each success, and then fails once with the new `Exceptions\PairsFailedException`, which lists every failed pair (`getFailures()`: field, locale, exception), is retryable if any failure was, and fires `TranslationFailed` as before. A configuration error or a rejected key (401, 403) still stops the job at once.
- The provider stack (provider, fallback chain, cache wrapper) was built once per process from the config at that moment, so a queue worker serving several tenants sent every tenant's content with the first tenant's key, URL and model, billed to that account, and ignored later changes to the default provider and the cache switch. `Support\ProviderFactory` now builds the stack from the config when it's used and reuses it while that config is unchanged. The default source locale is read from `app.locale` when it's used too (a value written by `app()->setLocale()` still doesn't count), and the usage-tracking listener checks `usage_tracking.enabled` when it handles an event, so tracking can be switched on at runtime. The README has a multi-tenant example.
- `translagenius:backfill` dispatched a job, run after run, for records whose translatable fields were all blank in the source locale. Those jobs requested nothing, but each run queued them again and counted them in the confirmation prompt. They are now skipped and reported as skipped, and the prompt's count equals the jobs dispatched.
- `SetLocale` ignored q-values (`fr;q=0.1, ar;q=0.9` picked `fr`), ignored `q=0`, and lowercased tags so a configured `pt-BR` never matched. Since the request locale becomes the source locale of the jobs it dispatches, this decided which text was translated from. It now reads `Accept-Language` per RFC 9110 (q-values, header order for ties, `*`, `q=0` excluded, malformed entries dropped), matches configured locales case-insensitively and sets them exactly as configured, and falls back from a region tag to its primary language when only that is configured (`fr-CA` to `fr`). With no match it still uses the first supported locale.
- A translation that nothing was written for, because its language was filled by someone else while the request was in flight or the record was deleted, was logged as `translated` and announced with `TranslationCompleted`. It is now logged as `discarded`, and no `TranslationCompleted` fires. Totals still equal what was billed.
- A fallback chain lost its members' `Retry-After`: when every member was rate limited, the job used its fixed backoff instead of the wait the providers asked for. `AllProvidersFailedException` now carries the shortest `Retry-After` among the members that may recover, and the job is released for it the same way as for a single provider (not on the last attempt). A member that failed for good is ignored; one that may recover but gave no wait means the fixed backoff applies.
- An empty or non-numeric numeric setting fell back to 0: `TRANSLATION_API_TIMEOUT=` disabled the HTTP timeout, so a provider that never answered could hold a queue worker until the queue killed it, and `TRANSLATION_CACHE_TTL=month` kept entries forever. Every numeric setting now uses its default when empty or not a number: `TRANSLATION_API_TIMEOUT`, `TRANSLATION_TEMPERATURE`, `TRANSLATION_MAX_TOKENS`, the `*_COST_PER_1K_*_TOKENS` rates (unknown, never 0), `TRANSLATION_CACHE_TTL`, `TRANSLATION_HTTP_RETRIES`, `TRANSLATION_HTTP_RETRY_AFTER_MAX`, `TRANSLATION_FALLBACK_HTTP_RETRIES`, `TRANSLATION_JOB_TRIES` and `TRANSLATION_JOB_BACKOFF` (non-numeric entries are dropped). An explicit `TRANSLATION_API_TIMEOUT=0` still means no timeout.
- A reply that was only whitespace threw `InvalidArgumentException` from `TranslationResult` instead of `TranslationFailedException`, so a fallback chain didn't move on, `TranslationFailed` never fired, and the billed tokens weren't logged. A blank reply (empty or whitespace only) is now a `TranslationFailedException`, billed as `unusable`: not retried within the request (the provider did answer), but retried by the queue, since it is usually a passing provider hiccup. One rule now decides whether a translation or source text is present everywhere (`Support\Text::isBlank()`: null, or empty after `trim()`), so `"0"` is a real value: a `"0"` translation is saved and never re-requested, and editing a source to whitespace requests nothing.
- **Translations on a real queue now start from the right language.** Since 3.x, the job decided the source language *inside the worker* (`app()->getLocale()`), which is the worker process's locale (normally `config('app.locale')`), not the locale of the request that saved the record. This affected every real (non-`sync`) queue setup: unless the request locale happened to equal the worker's, the job looked for source text in the wrong language and silently translated nothing (or translated the wrong text). The source locale is now captured when the job is dispatched and carried in its payload, for create, update and backfill. New `TRANSLATION_SOURCE_LOCALE` fixes it for apps that always author in one language (it wins over the request locale); `translagenius:backfill` gains `--source=` (default `TRANSLATION_SOURCE_LOCALE`, then `app.locale`) and shows the chosen locale in its prompt. A field whose source text is empty in that locale is skipped with a warning. A job already queued before upgrading carries no source locale and uses `TRANSLATION_SOURCE_LOCALE`, then the app's configured `app.locale`.
- The usage log now includes every billed request, so `SUM()` over it equals what the provider billed. Responses that reported usage but produced no saved translation were never logged: a truncated single reply, a truncated or unparseable batch (whose tokens were previously folded into the next row), an error response that still reported usage, every billed attempt by a fallback chain member that then failed over, and a translation discarded because its source changed again. Each now gets its own row, marked by a new `outcome` column (`truncated`, `unusable`, `failed`, `discarded`, `unsaved` for a translation whose save threw; saved translations are `translated`) and costed with the serving provider's rates. They are also dispatched as `Events\TranslationRequestBilled`.
- Editing a field's source-language text now updates its translations again. Since the per-locale "fill only what's missing" change, an update dispatched a job that found every locale already filled and did nothing, so the old translations stayed forever. A source change now re-translates and overwrites that field's other locales, except any target locale set in the same save, which is kept as provided. Each job carries a snapshot (a sha256 hash, so a job stays a few KB: 5 fields of 5 KB with 10 languages made a 277 KB payload, over SQS's 256 KB limit, and is now 5.4 KB) of the source it translates and of every stale target's value, and only writes a target if the stored source still matches and that target still holds its stale value: an older job can't overwrite a newer edit's translations, a hand edit made to a target after the source edit is never overwritten, and a retried job sends no requests for targets it already replaced. The same holds for an edit made while the create job is still translating: a translation of the old text is discarded under the lock (billed as `discarded`, no `TranslationCompleted`) instead of being saved, so the edit's own job fills that language from the new text. Creating records and `translagenius:backfill` still never overwrite.
- A custom job class without `Queueable` silently ignored `TRANSLATION_QUEUE_CONNECTION` / `TRANSLATION_QUEUE`; one warning naming the class is now logged per class per process.
- A retried translation job no longer re-translates (and re-bills) the field/locale pairs that had already succeeded: each pair is now saved as soon as it is translated. A partly translated record is reported by `notFullyTranslated()` while the job is in flight or after it fails.
- Translation jobs dispatched inside a database transaction no longer run before the commit (where `SerializesModels` couldn't find the row) or after a rollback, by default.
- Failed provider calls were retried regardless of status: the HTTP client's retry callback was passed in its sleep-duration slot, so a 401 or 404 was sent 3 times per job attempt, and a persistent 5xx up to 9 times across the job's own retries. 4xx responses other than 429 now fail on the first response at every layer.
- A translation cut off at the provider's output token limit (`finish_reason` `length`) was saved as if complete. It now fails with a non-retryable `TranslationFailedException` that names `TRANSLATION_MAX_TOKENS`; the job isn't retried, the `TranslationFailed` event fires, and a fallback chain moves on to its next provider.
- `TranslationResult->provider` now reports the `translagenius.providers` key the provider was resolved under (for example `gemini`). It was hardcoded to `openrouter`, so pointing the OpenAI-compatible provider at any other service logged usage under the wrong provider name and looked up the wrong cost rates.
- `TranslateFields` no longer re-requests translations that already exist. `prepareTranslations()` read each field through the model's magic accessor (`$model->{$field}`), which Spatie's `HasTranslations` resolves to the current locale's string only. Every other locale's existing translation was invisible to the job, so every save re-translated (and re-billed) every non-current locale. It now reads the full locale map via `getTranslations($field)`, and existing field/locale pairs are skipped as intended.
- The HTTP timeout is now actually applied to translation requests. It was defined in config (`api.timeout` in 3.x, now `translagenius.providers.openrouter.timeout` / `TRANSLATION_API_TIMEOUT`) but silently ignored.
- `TranslateFields` now has explicit `$tries`/`backoff()` and a `failed()` handler; translation failures propagate to the queue's native retry/failure handling instead of being silently swallowed.
- Added pessimistic locking (`lockForUpdate()`) around the job's write step to prevent a concurrent update's translation from being overwritten by a stale one.
- Stopped logging raw stack traces (a plausible path for the API key to end up in application logs via HTTP-client exception trace arguments).

### Changed

- The per-request "translation successful" and per-job "Translation completed successfully" log lines are `debug` now (were `info`). Warnings and errors are unchanged. The review migration adds an index on `(translatable_type, status, translatable_id)` for `pendingReview()` and review queues, and the usage-log migration one on `created_at`.
- The HTTP timeout default is now 60 seconds (was 10): replies of a few KB routinely take longer than 10. A request that timed out is logged as `failed` with null tokens, since the provider may have processed and billed it.
- Translation jobs have a timeout, `TRANSLATION_JOB_TIMEOUT`, or by default their own worst case (HTTP timeout x HTTP attempts per pair x pairs, 120 to 900 seconds). The queue connection's `retry_after` must be longer.
- Only one translation job runs per record at a time. Another job for that record is re-queued as a fresh copy after 10 seconds (it never uses up an attempt and is never dropped), so a create followed by a quick edit, or a redelivery, no longer pays for the same pairs twice. It needs a cache store with locks.
- Each provider keeps one HTTP connection open across its requests, within a job and across jobs with the same config. Every request used to open its own connection: a job of 2 fields x 8 languages made 16 TLS handshakes against a local server, now 1. `Http::fake()` works as before.
- Retry defaults: 1 quick HTTP retry (`TRANSLATION_HTTP_RETRIES`) for connection errors, 429 and 5xx, then the queue's 3 attempts (`TRANSLATION_JOB_TRIES`, backoff `TRANSLATION_JOB_BACKOFF`). A 429's `Retry-After` is honored: waited out in-request up to `TRANSLATION_HTTP_RETRY_AFTER_MAX` seconds (default 10), otherwise used as the queue release delay. Fallback chain members make no HTTP retries by default (`TRANSLATION_FALLBACK_HTTP_RETRIES=0`), so failover is immediate. Worst case per field/locale is 6 requests.
- `TRANSLATION_MAX_TOKENS` is unset by default (was 200), so no limit is sent and each provider's own default applies. Set it to cap output.
- `temperature` is optional: a null or empty value isn't sent. Only the `openrouter` preset still defaults it (0.3); the other presets leave it to the model.
- `Services\AutoTranslationService` → split into `Providers\OpenAiCompatibleProvider` (HTTP transport, prompt construction, response parsing - the OpenRouter-specific implementation) and `Services\Translator` (a thin class that resolves the configured provider and delegates).
- Introduced `Exceptions\TranslationFailedException`, replacing the misused `Illuminate\Http\Exceptions\HttpResponseException`.
- The translation prompt now uses the chat API's `system`/`user` message roles instead of one concatenated string.
